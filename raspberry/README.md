# raspberry — Raspberry Pi 4 (Wi-Fi-хотспот «WiFi-FREE-Taxi»)

Это не VPS, а физическая плата, воткнутая в домашний Wi-Fi. Её работа — раздавать собственную
открытую Wi-Fi-сеть с captive-порталом (реклама/заказ такси), локальным видео для детей и —
после нажатия кнопки на портале — интернетом через второй Wi-Fi (`wlan0`).

Всё, что относится к плате, лежит **в этом репозитории, в каталоге `raspberry/`** (раньше проект
жил в репозитории `tools`, каталог `nginx/` — теперь источник правды здесь).

> 🚧 **Статус деплоя (2026-09-20).** Код для выдачи интернета через `wlan0` написан и проверен
> изолированно на самой плате (виртуальный клиент в отдельном netns), но **на плату ещё не выкатан**:
> сейчас там работает прежняя версия из `/root/tools/nginx` (клиенты хотспота без интернета).
> Порядок переезда — в разделе «Деплой» ниже. Как только выкатим — убрать эту заметку.
>
> ⚠️ **До деплоя точка держится на ручном исправлении** (см. «Инцидент 2026-09-20»): внутри
> работающего контейнера вручную запущен `dnsmasq` с правильными ключами. При перезапуске
> контейнера/платы вернётся старый `entrypoint.sh` с `--no-daemon` и DNS может снова повиснуть —
> ещё одна причина выкатить эту версию.

## Как работает хотспот

Один контейнер (`nginx-wifi-ap-1`) с `hostapd`, двумя `dnsmasq`, `nginx` и Python-бэкендом
(`FastAPI` + `uvicorn`). `entrypoint.sh` при старте: ждёт 30 секунд, переводит `wlan1` в режим AP,
назначает `192.168.50.1/24`, запускает hostapd, `dnsmasq` (DHCP + DNS), портальный `dnsmasq`,
`wifi-fw.sh up`, `nginx` и `python3 ./back.py`. `PROFILE=dev` пропускает всё, что связано с AP.

### Клиент до авторизации (портал)

1. Клиент подключается к открытой сети, `dnsmasq` выдаёт адрес из `192.168.50.10–100` (аренда 24 ч).
2. Любой его DNS-запрос (в т. ч. на `8.8.8.8:53`) перехватывается правилом `REDIRECT 53 → 5354`
   и попадает в **портальный dnsmasq**, который отвечает `192.168.50.1` на любое имя
   (`address=/#/192.168.50.1`). Телефоны проверяют связь (`connectivitycheck.*`, `captive.apple.com`,
   `msftconnecttest.com` …), попадают на Pi, и сами открывают окно портала.
3. HTTP на любой внешний адрес заворачивается на `nginx` (`DNAT :80 → 192.168.50.1:80`), остальное
   наружу режется (`REJECT`, для TCP — `tcp-reset`, чтобы отказ был мгновенным).
4. `nginx` на любой запрос проверки связи отвечает 307 на портал (`/www/82.html`) через бэкенд
   `/auth-wifi-check/`. Портал работает и **без uplink** — ему интернет не нужен.
5. На портале: реклама и тарифы, форма «Оставьте номер телефона для заказа», кнопка
   «Развлечения для детей» (`/www/media.html`, видео из `/data/video` ≈ 17 ГБ, листинг `/video/`)
   и кнопка **«Подключиться к интернету»**.

### Клиент после нажатия «Подключиться к интернету»

1. Страница делает `POST /api/connect`. `back.py` берёт адрес клиента (`X-Real-IP` из nginx,
   верится только запросам с localhost) и добавляет его в `ipset wifi_authed` **на 24 часа**
   (`AUTH_TTL`, секунды). Работает только для адресов из `192.168.50.0/24`, кроме шлюза.
2. Клиент выпадает из «неавторизованных»: DNS идёт в основной `dnsmasq` (настоящий, апстримы
   `1.1.1.1`, `8.8.8.8`, `77.88.8.8`), а трафик — через `wlan0` с `MASQUERADE` (NAT).
3. Пока клиент в наборе, `back.py` отвечает на его captive-проверки «всё хорошо»
   (`generate_204`, iOS `Success`, Windows `Microsoft Connect Test` / `Microsoft NCSI`) — телефон
   считает сеть рабочей. Кэш DNS на телефоне живёт ≤ 60 с (`local-ttl`).
4. **В домашние и любые частные сети за uplink не пускают никого** (`10/8`, `172.16/12`,
   `192.168/16`, `169.254/16`, `100.64/10` → `REJECT`): открытый Wi-Fi не должен получить доступ к
   роутеру, NAS, компьютерам. Локальные имена портала (`mult.taxi`, `taxi.vkosarev.link`, …)
   резолвятся в `192.168.50.1` для всех.

Правила ставятся в цепочку `DOCKER-USER` (её выполняет Docker до своих правил, она переживает
перезапуск Docker) и в `nat/PREROUTING|POSTROUTING`; при остановке контейнера снимаются
(`wifi-fw.sh down`). Набор `wifi_authed` живёт в ядре: **после перезагрузки платы клиентам нужно
нажать кнопку заново** (портал вылезет сам).

Переменные `wifi-fw.sh`/`back.py` (значения по умолчанию подходят): `AP_IFACE=wlan1`,
`AP_IP=192.168.50.1`, `AP_NET=192.168.50.0/24`, `UPLINK_IFACE=wlan0`, `AUTH_SET=wifi_authed`,
`AUTH_TTL=86400`, `PORTAL_DNS_PORT=5354`, `FW_PREFIX=WIFI`.

### Заявки

Телефон из формы пишется в SQLite `py/back.sqlite3` (таблица `requests`: токен, телефон, IP клиента,
User-Agent, referer, статус, время) и в текстовый файл `py/data/<дата>-<телефон>.txt`.
Просмотр — `/api/list` (сейчас без авторизации, см. замечания).

## Деплой

Схема как в остальном репозитории: правки локально → коммит → push (по команде владельца) → на плате
`git pull` и `docker compose up -d --build`. Заливать файлы на плату руками (scp/pscp) не нужно.

### Переезд с `/root/tools/nginx` на этот репозиторий (один раз)

> Точка доступа будет недоступна ~1–2 минуты (сборка образа + 30-секундная пауза в `entrypoint.sh`);
> клиенты переподключатся сами. Лучше делать, когда в машине никого нет.

```bash
# 1. клонируем этот репозиторий на плату (если он приватный — понадобится токен, как на VPS)
sudo git clone https://github.com/vadim-kosarev/vps.git /root/vps

# 2. переносим данные, которых нет в git (база заявок и файлы заявок)
sudo cp -a /root/tools/nginx/py/back.sqlite3 /root/tools/nginx/py/data /root/vps/raspberry/nginx/py/

# 3. останавливаем старый проект и поднимаем новый (имя проекта — по каталогу `nginx`,
#    поэтому контейнер и образ называются как раньше: nginx-wifi-ap-1 / nginx-wifi-ap)
cd /root/tools/nginx && sudo docker compose down
cd /root/vps/raspberry/nginx && sudo docker compose up -d --build
```

Старый `/root/tools/nginx` оставляем как запасной вариант (откат: `docker compose down` в новом
каталоге и `docker compose up -d` в старом). Локальная правка `82.html` на плате («г.Кстово, г.Бор»)
уже учтена в копии в этом репозитории.

### Обычное обновление

```bash
cd /root/vps && sudo git pull
cd raspberry/nginx && sudo docker compose up -d --build     # менялись Dockerfile/entrypoint/dnsmasq/wifi-fw.sh
# менялись только py/ или var/www/ (они монтируются в контейнер): достаточно
sudo docker compose restart
```

### Проверка после деплоя

```bash
sudo docker logs --tail 40 nginx-wifi-ap-1          # "Setting up NAT/firewall", ошибок wifi-fw.sh нет
sudo iptables -S DOCKER-USER                        # есть -j WIFI_FWD
sudo iptables -t nat -S PREROUTING                  # есть -i wlan1 -j WIFI_CAPTIVE
sudo docker exec nginx-wifi-ap-1 ipset list wifi_authed   # кто сейчас авторизован
```
С телефона: подключиться к `WiFi-FREE-Taxi` → должно вылезти окно портала → «Подключиться к
интернету» → открываются обычные сайты; `http://192.168.55.1` (роутер) не открывается.

## Как это проверялось

Перед деплоем логику проверили на самой плате, не трогая живую точку доступа: виртуальный клиент
в отдельном сетевом пространстве имён (`veth` + `unshare -n`), правила с другим префиксом
(`FW_PREFIX=TST`) и набором `tst_authed`, в одноразовом контейнере из образа `nginx-wifi-ap`.
Проверено: до авторизации HTTP уходит на портал, HTTPS и DNS наружу отбиваются/подменяются;
после — HTTP/HTTPS/DNS идут в настоящий интернет; `192.168.55.x`, `192.168.56.x`, `10.x` недоступны;
`up` идемпотентен, `down` убирает все правила. Для `back.py` — с настоящим `ipset`: авторизация,
ответы на captive-проверки Android/iOS/Windows, отказ (403) для внешних адресов, адреса шлюза и
попытки подделать `X-Real-IP` не с localhost. Оба конфига `dnsmasq` проверены `dnsmasq --test`.
**Не проверено на реальных телефонах** (Android/iOS
сами решают, показывать ли окно портала) — после деплоя проверить руками.

## Инцидент 2026-09-20: хотспот «не даёт ни интернет, ни портал»

**Симптом:** телефон подключается к `WiFi-FREE-Taxi`, пишет «нет интернета», `http://ya.ru`
не открывается («адрес не найден»), окна с рекламой нет.

**Причина:** `dnsmasq` (он же DHCP-сервер) висел и не читал сокеты — очередь приёма `Recv-Q` на
`192.168.50.1:53` и `0.0.0.0:67` стояла на максимуме, DNS и DHCP не отвечали никому (даже самой плате).
`entrypoint.sh` запускал его с `--no-daemon` — это режим отладки (`-d`), в котором `dnsmasq` **не
создаёт дочерних процессов для TCP-запросов**. Клиент (`192.168.50.24`, компьютер `STARLIGHT`) открыл
несколько TCP-соединений на порт 53 и не дочитал/не закрыл их — единственный поток `dnsmasq` встал
в блокирующем `read()` навсегда (`/proc/PID/stack`: `tcp_recvmsg`). Зависание могло начаться задолго
до жалобы и повторится, стоит любому клиенту сделать то же самое.

**Что сделано:** зависший процесс убит, вместо него внутри контейнера вручную запущен
`dnsmasq --keep-in-foreground --log-facility=- --local=/#/ --conf-file=/etc/dnsmasq.conf`.
В репозитории `entrypoint.sh` переведён на `--keep-in-foreground` (оба `dnsmasq`), а портальный
конфиг получил `local=/#/`, чтобы на AAAA-запросы (IPv6) отвечать пустым ответом, а не `REFUSED`
(без upstream-серверов `dnsmasq` иначе отказывает; у телефонов это может выглядеть как сбой DNS).

**Как узнать, что повторилось:**
```bash
sudo ss -ulnp | grep -E ":(53|67) "     # Recv-Q у dnsmasq ~ 0; если сотни тысяч — завис
sudo docker top nginx-wifi-ap-1 -eo pid,args | grep dnsmasq
```

## Замечания по состоянию (на 2026-09-20)

Не исправлялось — только зафиксировано.

**Безопасность**
- Открытая сеть `wlan1` + `sshd` слушает на всех интерфейсах + `PasswordAuthentication yes` +
  `INPUT` в iptables `ACCEPT` + простой пароль пользователя `pi` с `sudo` без пароля: любой
  клиент хотспота может пробовать войти на плату по SSH и получить root. После выдачи интернета
  такой хотспот станет ещё привлекательнее — стоит ограничить SSH интерфейсом `wlan0` (или включить
  только ключи) и сменить пароль. Правила `wifi-fw.sh` защищают только домашние сети *за* uplink, но не
  саму плату.
- Порт 1501 и Portainer (9443/8000) также доступны клиентам открытой сети.
- Эндпоинт `/api/list` без какой-либо авторизации отдаёт список собранных телефонных номеров —
  это персональные данные, доступные любому клиенту хотспота.
- Портал собирает телефоны пассажиров: стоит помнить про требования 152-ФЗ, если хотспот будет
  использоваться по-настоящему.
- Авторизация клиента «по адресу»: тот, кто сменит IP на чужой авторизованный, получит его интернет.
  Для бесплатного Wi-Fi это приемлемо, для защиты чего-то ценного — нет.

**Обслуживание**
- Часы платы после загрузки стартуют с устаревшего времени (нет RTC) и выравниваются по NTP только
  когда есть uplink. Пока uplink нет (например, в машине), время в логах и в заявках неверное.
- Ожидают обновления ~340 пакетов `apt`.
- В Docker накопилось ~15 «висящих» образов (`<none>`, по ~590 MB каждый, слои общие) от
  пересборок `nginx-wifi-ap` — можно почистить `docker image prune`.
- В `who` висят 8 SSH-сессий с `192.168.50.24` — этот адрес хотспот выдал компьютеру `STARLIGHT`
  (по MAC в DHCP-аренде). Метки времени в выводе битые (дата 1970), давно ли сессии открыты — не выяснено.
- Бэкапа `py/back.sqlite3` и `/data/video` нигде нет, cron-задач нет.
- Если uplink пропадёт, портал и мультики работают, а авторизованные клиенты остаются без интернета.

## Управление

```bash
# состояние
sudo docker ps
sudo docker logs --tail 50 nginx-wifi-ap-1
sudo docker exec nginx-wifi-ap-1 iw dev wlan1 info       # режим AP, SSID, канал
sudo docker exec nginx-wifi-ap-1 ipset list wifi_authed  # авторизованные клиенты (после деплоя)

# перезапуск портала/точки доступа
cd /root/vps/raspberry/nginx && sudo docker compose restart

# выдать интернет клиенту вручную / забрать обратно (после деплоя)
sudo docker exec nginx-wifi-ap-1 ipset add wifi_authed 192.168.50.35 timeout 3600
sudo docker exec nginx-wifi-ap-1 ipset del wifi_authed 192.168.50.35
```
